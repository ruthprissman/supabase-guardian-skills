# פרומפט להחלה על פרויקט קיים

הדבק את כל מה שמתחת לקו בשיחת Claude Code **בתוך הפרויקט** שרוצים לעדכן.
מיועד לפרויקטים שכבר רץ בהם גיבוי יומי ל-Drive ללא הצפנה.

כל אזהרה כאן נובעת מתקלה אמיתית שכבר עלתה סבב עבודה — אל תקצר אותן.

---

הגיבוי היומי ל-Drive בפרויקט הזה מעלה עותק **גלוי** של כל בסיס הנתונים. תקן.

**אל תניח כלום על המימוש — קרא קודם את `scripts/backup/backup.mjs` ואת
`.github/workflows/backup.yml`.** יש שני זרמים שונים בפרויקטים שלי: אחד מבוסס
`pg_dump` עם `SUPABASE_DB_URL`, ואחד מבוסס REST עם `SUPABASE_SERVICE_ROLE_KEY`.

## 1. הצפנה — בכל מימוש

```
openssl enc -aes-256-cbc -pbkdf2 -iter 600000 -salt -in F -out F.enc -pass env:BACKUP_ENCRYPTION_KEY
```

- `openssl` דרך ה-CLI, **לא** `node:crypto` — מסלול השחזור לא ייתלה בקיום הריפו.
- **`.trim()` על המפתח, עם הערה בקוד שמסבירה למה.** `-pass env:` מוסר את המשתנה
  verbatim כולל ירידת שורה, בעוד ששורת בקשת הסיסמה בפענוח **מסירה** אותה. בלי
  trim, סוד שנשמר עם `\n` תועה נותן `bad decrypt` נצחי מול מפתח שנראה תקין לגמרי.
- מפתח חסר או ריק אחרי trim = **עצור את הריצה**. אין נפילה חזרה לגלוי.
- מחק את הטקסט הגלוי מיד עם יצירת הצופן — לא בסוף `main()`, שלא רץ אם ההעלאה נכשלת.
- הצפן **גם את האקסל**. שנה mimeType ל-`application/octet-stream`.
- המפתח עובר ב-`-pass env:` ולא ב-argv.

## 2. auth — רק אם המימוש הוא pg_dump

בדוק אם בסכמת `public` יש FK ל-`auth.users(id)`. **אל תבדוק את זה ב-grep על
`supabase/migrations/`** — במיגרציות של פרויקט Lovable חסרות בדרך כלל הראשונות,
אלה שיצרו את `public.users` ואת שער ההרשאות, ולכן grep שחוזר ריק הוא
**false negative מובנה** ולא ראיה שאין FK. שאל את בסיס הנתונים החי:

```sql
select conrelid::regclass as tbl, conname
from pg_constraint
where contype = 'f' and confrelid = 'auth.users'::regclass;
```

אם יש FK, **הגיבוי הנוכחי אינו בר-שחזור** — לא "חסרות התחברויות", אלא הטעינה
לפרויקט חדש נכשלת על האילוץ. הוסף קובץ שלישי:

```
pg_dump --data-only --table=auth.users --table=auth.identities
```

- **data-only בלבד** — פרויקט Supabase חדש כבר מגיע עם סכימת `auth`.
- בשחזור: **auth לפני public**.
- כישלון בדאמפ ה-auth **לא יפיל את הגיבוי הראשי**: העלה קודם את מה שעבד, ורק אז
  הפל את הריצה (מייל אדום, לא שורה בלוג).

**ארבע מלכודות שיעלו לך שעות אם תדלג עליהן:**

1. **החיבור חייב להיות `postgres`, לא `backup_reader` ייעודי.** אפשר להעניק
   `select` על `auth.users`/`auth.identities`, אבל **לא** `usage` על הסכימה `auth`
   — היא בבעלות `supabase_auth_admin`, ו-`set role supabase_auth_admin` נכשל ב-
   `42501`. אין בפרויקט זהות שיכולה להעניק את זה. תעד ללקוחה שהמחיר הוא שתפקיד
   הגיבוי כבר אינו קריאה-בלבד.
2. **`GRANT` שנכשל מחוסר סמכות לא מחזיר שגיאה** — PostgreSQL מוציא `WARNING`
   ו-Supabase מציג `Success. No rows returned`. אמת תמיד:
   `select has_schema_privilege('<role>','auth','USAGE');`
3. **מחרוזת החיבור: Session pooler, פורט `5432`.** לא `6543` (transaction pooler —
   `pg_dump` לא עובד מולו), ולא Direct connection (IPv6 בלבד; GitHub Actions נופל
   על `ENETUNREACH`). הכתובת חייבת להכיל `pooler`, והמשתמש הוא
   `postgres.<project-ref>`. סיסמת `postgres` אינה ניתנת לצפייה בדאשבורד, רק
   לאיפוס — ואיפוס כזה **מגיע ל-pooler תוך פחות מדקה**, אל תמתין שעות.
4. **התקן `postgresql-client-17`, ואל תאמין ל-`pg_dump --version`.** שרת Supabase
   הוא 17.x ו-`pg_dump` 16 מסרב לגמרי (`aborting because of server version
   mismatch`). המלכודת: גם אחרי התקנת 17, `pg_dump --version` על הרנר מדפיס
   `16.15` — `pg_wrapper` עונה לפי ה-cluster המקומי אבל משתמש בלקוח החדש ביותר
   מול מארח מרוחק. הראיה היחידה שקובעת היא כותרת הדאמפ:
   `zcat dump.sql.gz | grep -m1 'Dumped by pg_dump'`.

אם המימוש הוא **REST + service_role**: אין גישה ל-`auth.users` דרך PostgREST,
וה-Auth Admin API לא מחזיר גיבובי סיסמאות. אל תמציא פתרון — **תעד** ב-README
שבשחזור כל המשתמשות יאפסו סיסמה.

- **במימוש REST בדוק גם את דאמפ ה-INSERT** — שלושה באגים שתוקנו בתבנית ב-28.10.2026
  (`pgArrayLiteral` / `sqlLiteral` ב-`assets/backup.mjs` של הסקיל): עמודת מערך
  (`text[]`, `uuid[]`…) נכתבת כ-array literal לפי סוג העמודה מה-OpenAPI spec, לא
  כ-JSON ש-Postgres דוחה; עמודת `json`/`jsonb` נכתבת תמיד כטקסט JSON, גם כשהערך
  מחרוזת, מספר או בוליאני; והנתונים עטופים ב-`session_replication_role = replica`,
  אחרת סדר הטבלאות לפי השם שובר את ה-FK בשחזור לטבלאות ריקות. replica מדלג גם על
  ה-FK ל-`auth.users`: תעד ב-README שבשחזור לפרויקט חדש יוצרים קודם את משתמשות
  ה-auth באותם `id`, אחרת הטעינה מצליחה בשקט עם הפניות למשתמשות שאינן קיימות.
  אם טריגר על `auth.users` ממלא טבלה ב-public, תעד גם לרוקן אותה אחרי יצירת
  המשתמשות ולפני הטעינה, אחרת היא נכשלת על מפתח כפול.

## 3. תיעוד

README: ייצור המפתח (`openssl rand -base64 48`), שמירה בשני מקומות, פקודת הפענוח,
סדר הטעינה. מה **לא** מכוסה: קבצי Storage, pg_cron, Edge Functions, סודות הפרויקט.
ציין ש-`psql` לא מגיע עם Git for Windows. `CHANGELOG.md` בעברית תחת `[Unreleased]`.

## 4. אימות — אל תדווח "בוצע" בלעדיו

- סבב הצפנה-פענוח מלא, כולל תוכן בעברית.
- **בדוק במפורש** שקובץ שהוצפן עם מפתח שיש בו `\n` בסוף נפתח בפענוח ידני עם
  המפתח הנקי. זו הרגרסיה שה-trim מונע.
- הרץ את ה-workflow ואמת בלוג שהקבצים עלו עם `.enc`.
- **ואז את הבדיקה שכולם מדלגים עליה: הורד את הקובץ שהועלה מ-Drive בחזרה ופענח
  אותו.** כל מה שלפני זה בודק את הצד שלך; רק זה בודק את מה ש**באמת שמור**.
  הדרך הנקייה היא job זמני ב-CI שמושך את הקובץ החדש ביותר מהתיקייה עם
  `GOOGLE_REFRESH_TOKEN`, מפענח עם ה-secret, ומריץ `gzip -t` וספירת `^COPY ` —
  כך איש אינו צריך להחזיק את המפתח ביד. מוחקים את ה-job אחרי שהוא ירוק.
  ⚠ בבחירת "הקובץ האחרון": גם דאמפ ה-auth מסתיים ב-`.sql.gz.enc` והוא מועלה
  אחרון — החרג אותו במפורש, אחרת תבדוק אותו פעמיים ואת דאמפ ה-public כלל לא.
- השאר בריפו את `scripts/backup/verify-backup.sh` כדי שהלקוחה תוכל לחזור על
  הבדיקה מתי שתרצה, עם העותק שלה של המפתח.

## 5. בסוף — רשימת מה שאני צריכה לעשות ידנית

מפתח + Secret, והחלפת מחרוזת החיבור אם צריך.

**את הגיבויים הגלויים הישנים אין צורך למחוק ידנית** — הניקוי מוחק כל קובץ
בתיקייה שגילו מעל `RETENTION_DAYS`, בלי לסנן לפי שם, אז הם נעלמים מעצמם עד
התאריך הזה. תגיד לה מהו התאריך, ושאם היא רוצה שהחשיפה תיעלם היום — המחיר הוא
אובדן נקודות השחזור שלפני המעבר להצפנה.
